## Confirmed root cause
The canonical identity is `device_access.device_id` (P-256 public-key digest), and browser multi-account vault only swaps locally saved credentials/progress. `device_access` has unique indexes on `(person_role, person_code)` and `phone`, preventing the same registered person from enrolling another device. Learning progress (`device_profiles`), training resources/sessions, manager assignments, quotas and audit all reference devices. **No portable login/password user-account credential flow currently exists for this app.** Pure UI/login changes cannot fix cross-device identity.

## Desired acceptance contract
1. **Person-first account:** one stable `account_id` per learner, manager or teacher; identity and approval in owning BOIECH D1, independent of device. Register **once** and submit pending review. User can authenticate to see PENDING / rejected status, but cannot enter protected modules before approved. Three role choices remain: learner, manager, teacher. Manager account approval and operational grant only Owner/App-Manager; managers approve learner/teacher registrations only.
2. **Account on many devices:** login with account credential on a new browser creates a new device binding / P-256 key, **without** re-registering or reapproving the person. Independently block/revoke device sessions without revoking the person; blocked account stays blocked on all devices. Support multiple users on one device and the same user on multiple devices. Sessions expire, rotate and revoke; rate-limit authentication, protect against enumeration, replay, CSRF/session fixation; provide secure password reset/recovery.
3. **Password confidentiality:** never store or transport plaintext beyond password submission over HTTPS; use reviewed one-way password hashing with a unique salt and safe verifier, not a handmade reversible cipher. Never return, log, display, export, email, or reveal passwords/password hashes to any manager **or Owner**. No password in localStorage, browser account vault, D1 audit, logs, or read-all endpoints. Authentication must not rely solely on client-claimed account ID/role.
4. **Permissions are separate:** existing `manager.approve.registration` for all pending learners/teachers with **minimal necessary fields only**, `manager.manage.assigned` for previously authorized assignment/scheduling/block functions, and **new distinct Owner-granted** `registrants.read.all` for only specifically selected manager accounts. Grant/revoke only via verified App-Manager Owner server gate, signed bridge, owner-D1 CAS + immutable audit + fresh independent raw D1 readback, fail-closed when revoked or expired. Do not grant broad read by role or device, and do not change global `50 learners / 5 teachers` quota. Quota counts DISTINCT APPROVED ACCOUNTS, not logins/devices.
5. **Privacy:** read-all excludes password material, session tokens, P-256 private keys, secrets and unnecessary highly sensitive data. Field-level filtering, per-access audit (viewer ID, account target, purpose, timestamp), query limits and authorization checks at BOIECH server on every read. The list of privileged staff may be Owner-only in administration, but **no covert/unaudited access or misleading privacy notices** to registrants; tell users their registration data is processed by appropriately authorized staff under a visible privacy notice.
6. **Compatibility:** preserve old approved/pending/blocked users, statuses, roles, profile progress/attempts, video analysis, offline queues, course certificates, payments, class/teacher schedules and earlier audit. Add `accounts`, `account_credentials`, `account_devices`, `account_manager_permissions` (or equivalent) with new indexes/migrations, mapping legacy device ID to account ID **without** creating fake duplicate identities. Do not drop unique indexes or overwrite existing device tables blindly; perform deterministic dry-run / conflict reports, backfill, independent D1 readback, rollback/migration gate. Keep feature flag OFF until fully verified.
7. **Ownership:** BOIECH owns identity, sessions, passwords, D1, registration/review queue, progress and quota. App-Manager ONLY owns Owner ability to grant/revoke manager capabilities and see control-plane audit/status via authenticated contract; it must never store user password/profile dumps or become the primary identity database. Demo `/xem-thu-can-bo-quan-ly` stays read-only.
