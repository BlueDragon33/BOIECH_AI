# Training management in Bơi Ếch AI

The user requests three registration choices in this order: Học viên, Cán bộ quản lý, Giảng viên, and a dedicated manager workspace allocating registered people, classes, rooms, buildings and time. State, color and explicit remaining/missing counts must make allocation understandable. Existing canonical Cloudflare origins and Constitution1.3.0 remain in force; the Hub main contract still reports1.3.0.

Implement within the existing Boi app and D1 database, with a small Central admin companion for explicit manager permission. A separate app/database would duplicate identities and conflict with shared administration; a UI-only mock would not satisfy the request. Use existing signed device identity, people registry and teacher class fields. No dependency addition, new site, automatic production publishing or sample data in real counters.

Registration role `manager` expresses requested responsibility. It never grants global directory/scheduling access by itself, including auto-approved registrations. Add a default-off manager permission, cleared atomically when identity role/code changes. Only the existing Owner control boundary can grant/revoke it for a registered, currently approved manager. Ordinary device access/payment/expiry remain independent. Central manages this permission; training managers do not gain Owner/device/payment/content-editing rights.

Manager workspace has overview, schedule, people, classes, rooms and buildings. Real registered learners/teachers form the directory, including pending/blocked/expired status. Assign learners to one class and teachers to their existing list of up to12 classes, updating the canonical class_name fields so existing teaching views observe assignments. Active class names are stable once assigned; no duplicate roster. Buildings/rooms/classes have active/unavailable/archived state; room and class capacities and required teacher counts are editable. Status labels accompany colors: green available, blue allocated/full, amber missing, red conflict/over-capacity, grey inactive. Exact booking interval is visible and filters room/teacher availability. Empty data shows zeros and a create-building/class next step.

Sessions select class, room, registered teacher and explicit start/end instants. Store UTC instants, display browser local time with timezone label. Scheduled/completed/cancelled lifecycle; no destructive deletes. Reject invalid intervals, unavailable resources, unapproved/expired staff, unassigned teachers, capacity excess and overlapping room/class/teacher sessions. Adjacent intervals are valid. Database constraints/triggers protect concurrent reservations and capacity changes. Resource/session optimistic versions reject stale edits. Permission is checked again in mutation SQL. Atomic receipts keyed by request ID make retries safe; changing an intent must use a fresh ID. Success requires current owning D1 readback; no optimistic false success.

Forms preserve drafts after errors, expose specific errors, prevent duplicate submission, and bound network waits. Mobile layouts use cards, controls >=44px and labels; colors never carry meaning alone. Read only directory fields required for allocation, without phone/key/payment-proof/video data. Large result sets fail visibly rather than silently reporting partial totals. Production migration and new permissions require the existing separate explicit release gate; deliver tested PRs before requesting release approval. Rendered mobile/composited-contrast evidence must remain UNVERIFIED if the browser cannot render an authorized test environment.

Capacity admission clarification: when a configured class/accepted room is full, new registration is saved but automatic approval remains pending with a specific audit reason. Approval, renewal or unblock cannot activate an extra counted learner until the manager reallocates them or corrects capacity. These checks do not grant management/content/payment authority or modify a paid expiry as a side effect.
